# AVE 双轴云台控制固件 —— 项目计划文档

## 1. 项目概况

### 1.1 项目定位

本项目是**基于 STM32F407 的双轴云台（水平-俯仰）控制固件**，用于驱动两路张大头（ZDT）Emm42 闭环步进电机，实现：

- **视觉自动跟踪**：接收视觉模块（**Sipeed MaixCAM**，运行 MaixHub 训练的 YOLO 目标检测模型）通过串口发来的目标像素坐标，用增量式比例-积分-微分（PID）算法闭环控制云台转动，把目标锁定在画面中心；

  > ⚠️ **YOLO 推理不在本单片机上运行。** STM32F407 既无神经网络加速单元，算力与内存也不足以跑目标检测。
  > 检测在 MaixCAM 上完成后，本固件**只收到三个整数** `cx, cy, flag`。上下游接口约定见 **§6**。
- **激光指示控制**：由上位机标志位或云端命令控制红外激光模组通断；
- **本地文本命令控制**：`PAN/TILT/GOTO/STOP/ZERO/...` 等以美国信息交换标准码（ASCII）编成的文本命令，便于用串口助手直接调试；
- **云端控制（可选）**：通过 ESP8266 无线模组接入消息队列遥测传输协议（MQTT）服务器，接受远程命令并周期性上报云台状态。

### 1.2 技术形态

| 项目 | 说明 |
| --- | --- |
| 运行形态 | **FreeRTOS 多任务架构**（CMSIS-RTOS2 接口）：串口逐字节中断接收写入环形缓冲，任务侧按行读取；4 个任务按职责划分优先级（详见 4.2 节）。取代原方案的裸机超级循环 |
| 视觉端（**不在本固件内**） | **Sipeed MaixCAM** 运行 MaixHub 训练的 YOLO 模型，把目标框中心换算成像素坐标后经 `USART1` 发送。**本固件不做任何图像处理或神经网络运算**，只解析坐标 —— 详见 **§6** |
| 驱动库 | 意法半导体官方硬件抽象层驱动库（F4 系列固件包 V1.28.3） |
| 配置方式 | 图形化配置工具只生成了系统节拍与底层初始化骨架；**所有外设（串口/通用输入输出/定时器）均手写初始化**（自包含板级支持包，不依赖额外生成文件） |
| 编译工具链 | 开发环境 V5（编译器 AC5，启用 C99 标准，优化等级 `Optim=4`），生成烧录文件 |
| 功能开关 | `AVE_ENABLE_VISION` / `AVE_ENABLE_CLOUD` / `AVE_ENABLE_MOTOR_READBACK` / `AVE_ENABLE_STEPDIR_BACKEND` / `AVE_ENABLE_STARTUP_MOTOR_TEST`（详见 1.3 节） |

### 1.3 当前默认配置（出厂状态）

| 开关 | 默认值 | 影响 |
| --- | --- | --- |
| `AVE_ENABLE_VISION` | `1` | 视觉跟踪**开启**，`USART1` 输入生效 |
| `AVE_ENABLE_CLOUD` | `0` | 云端接入**关闭**，`USART3`、ESP8266 驱动、MQTT 协议层、云端状态机整体不参与编译、不初始化 |
| `AVE_ENABLE_MOTOR_READBACK` | `0` | 关闭云台的周期性数据回读（`QPOS` 等命令仍可手动触发） |
| `AVE_ENABLE_STEPDIR_BACKEND` | `0` | 关闭传统"脉冲/方向"脉冲后端，改用串口协议驱动电机 |
| `AVE_ENABLE_STARTUP_MOTOR_TEST` | `1` | 上电自动做一次两轴点动自检（约 0.9 秒） |

## 2. 硬件平台

### 2.1 主控

| 项目 | 参数 |
| --- | --- |
| 主控芯片 | **STM32F407VGT6**，100 引脚方型扁平封装（LQFP100） |
| 内核 | ARM Cortex-M4F（含单精度浮点运算单元），最高主频 168 兆赫 |
| 存储 | 1 兆字节闪存 / 192 千字节静态随机存储器（含 64 千字节紧耦合内存） |
| **实际运行主频** | **168 兆赫**（内部高速时钟 HSI 16 兆赫经锁相环倍频：`PLLM=8`、`PLLN=168`、`PLLP=2`），见 `main.c: SystemClock_Config()` |
| 总线频率 | 内核总线 168 兆赫；低速外设总线（`APB1`）42 兆赫；高速外设总线（`APB2`）84 兆赫 |
| 中断分组 | `NVIC_PRIORITYGROUP_4`（16 级抢占优先级，无子优先级） |
| HAL 时基 | 由 **`TIM7`** 提供，抢占优先级 **15** —— **不使用 `SysTick`**，`SysTick` 已交给 FreeRTOS |
| 中断优先级 | `USART1` / `USART2` / `USART3` 均为 **5**；`TIM6`（脉冲节拍，默认不启用）为 **5** |
| 调试接口 | 串行线调试（SWD），配置见 `MDK-ARM/DebugConfig/AVE_STM32F407VG.dbgconf` |

> 🔴 **主频必须为 168 兆赫 —— 这是硬性要求，不是性能优化。**
>
> 本工程三路串口（`USART1`/`USART2`/`USART3`）以 115200 波特率**逐字节中断**接收：
> 每路 11520 字节/秒 × 3 路 ≈ **34560 次中断/秒**。换算到时钟周期：
>
> | 主频 | 每次中断可用周期 | 余量 |
> | --- | --- | --- |
> | 16 兆赫（原方案） | 约 463 | 一次「中断进出 + `HAL_UART_IRQHandler` + 回调 + 写环形缓冲」约需 200–400 周期 → **接近饱和** |
> | 168 兆赫（本方案） | 约 4860 | 约 12 倍余量 |
>
> 也就是说，在 16 兆赫下光是把三个串口的字节搬进缓冲区就几乎用满了处理器，
> 再叠加浮点 PID 与任务切换必然丢字节。**原方案自己也提到了这个隐患但没有给出解法。**

> 🔴 **任何中断的抢占优先级数值不得小于 5。**
>
> FreeRTOS 的 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`（见 `Core/Inc/FreeRTOSConfig.h`）。
> 抢占优先级**数值小于 5**（即优先级更高）的中断**禁止调用任何 `xxxFromISR()` 接口**，
> 且**禁止调用任何可能引起任务切换的 API**。
>
> 原方案给「定时器 6」分配优先级 **4**（4 < 5），一旦在该节拍中断里调用 RTOS 接口就会命中
> `configASSERT` 断言并死机。已统一改为 **5**。
>
> 另注：`HAL_IncTick()` 由 `TIM7` 中断（优先级 15）调用，它同样不得出现在优先级 < 5 的中断里。

### 2.2 外设与执行机构

| 部件 | 型号 / 规格 | 接口 | 备注 |
| --- | --- | --- | --- |
| 水平轴电机 | 张大头 **Emm42 闭环步进电机** | `CR_UART`（晶体管-晶体管逻辑电平串口），地址 **1** | 与俯仰轴共用一条串口总线 |
| 俯仰轴电机 | 张大头 **Emm42 闭环步进电机** | `CR_UART`（晶体管-晶体管逻辑电平串口），地址 **2** | 同上 |
| 视觉模块 | **Sipeed MaixCAM**（运行 MaixHub 训练的 YOLO 模型） | `USART1`，115200 波特率，8 位数据/1 位停止/无校验，约 20 赫兹 | 发送文本行 `cx,cy,flag\n`；**只发不收**，单向接线即可。接口硬约束见 §6.3 |
| 无线模组 | ESP8266（内置 AT 指令固件） | `USART3`，115200 波特率 | 仅当 `AVE_ENABLE_CLOUD=1` 时使用 |
| 激光模组 | 红外激光 | 通用输入输出推挽输出 | 由视觉标志位或云端命令控制，默认关闭 |
| 云平台 | 物联网平台消息服务器 | 传输控制协议端口 1883 | 地址与凭据一律见 `AVE_secrets.h`（**不在本文档中出现**） |
| 备用驱动接口 | A4988 / DRV8825 / TB6600 等脉冲型驱动器 | 通用输入输出加定时器 6 | 默认关闭（`AVE_ENABLE_STEPDIR_BACKEND=0`） |

### 2.3 通信参数

| 总线 | 波特率 | 数据位 / 停止位 / 校验 | 用途 |
| --- | --- | --- | --- |
| `USART1` | 115200 | 8 / 1 / 无 | 视觉模块（MaixCAM）输入（本工程只解析，不使用发送） |
| `USART3` | 115200 | 8 / 1 / 无 | 无线模组 AT 指令与传输控制协议透传 |
| `USART2` | 115200 | 8 / 1 / 无 | ZDT 电机总线（多机共用），**校验字节 `DATCHECK` = 0x6B** |

> **关于 `USART6`（`PC6`/`PC7`）**：当前架构中**未使用**。
> 原设计里它被分配给俯仰轴电机，改为双轴共用一条 `USART2` 总线后即无用途。
> 工程中可移除，也可保留备用（保留不影响功能）。
>
> ⚠️ 无论去留，只要它在工程中被初始化，其 NVIC 优先级就必须 ≥ 5，
> 且中断处理函数内不得调用任何非 `FromISR` 的 RTOS 接口。

> 🔴 **原方案缺少独立调试串口 —— 已补上。**
>
> 三路串口原本是**全满**的：`USART1` 给视觉模块、`USART2` 给电机总线、`USART3` 给 ESP8266。
> 但 §1.1 又承诺「本地文本命令控制，便于用串口助手直接调试」—— 两者矛盾，没有口可插。
> §7.3 给出的实际做法是把串口助手接到**视觉串口**上，那意味着调试时必须拔掉视觉模块。
>
> **修正**：把 `USART3` 兼作调试串口。因为 `AVE_ENABLE_CLOUD` 默认为 **0**，
> 云端未启用时 `USART3` 本就空闲、不初始化、无人使用，正好给串口助手。
>
> | 条件 | `USART3` 归属 |
> | --- | --- |
> | `AVE_ENABLE_CLOUD = 0`（默认） | **调试串口** —— 接收文本命令、输出日志 |
> | `AVE_ENABLE_CLOUD = 1` | 无线模组 ESP8266 |
>
> 这样开发全程（第 1～3 周）都有一个稳定可用的交互口，不受视觉模块是否在场影响。

### 3.1 引脚分配表（定义在 `AVE/AVE_board.h`）

#### USART1 —— 视觉模块 MaixCAM

| 信号 | 单片机引脚 | 复用功能 | 对接 |
| --- | --- | --- | --- |
| 发送 | `PB6` | `GPIO_AF7_USART1` | → MaixCAM 接收端（**本工程不使用，可悬空**） |
| 接收 | `PB7` | `GPIO_AF7_USART1` | ← MaixCAM 发送端（`cx,cy,flag\n`） |

> 🔧 **2026-09-25 由上板实物改定：原方案是 `PA9`/`PA10`。**
>
> 实板上 `PA9` / `PA10` **没有引到排针**（也没接任何板载器件），物理上接不出线，
> MaixCAM 根本连不上。而本链路**只收不发**，实际只需要**一个**引脚，
> 所以可选范围很宽。
>
> STM32F407 的 USART1 有两组复用引脚：`PA9/PA10` 或 **`PB6/PB7`**（都是 AF7）。
> 本板 `PB6/PB7` 有引出 → **只换引脚、不换串口**：
> `huart1` 句柄不变、通道枚举 `AVE_UART_CAM` 不变、业务代码与心跳行**一行都不用改**。
> 改动落在三处：CubeMX 引脚分配、`AVE/AVE_board.h` 的引脚宏（纯文档）、本节。
>
> 🔴 **教训**：引脚表必须在**拿到实物之后**复核一遍。
> 这份表在纸面上一直是"对的"，错的是它和硬件的关系 ——
> 而这类错误**不会有任何编译或运行症状**，只会在接线那一刻才暴露。

### 3.2 接线示意

```
                    ┌───────────────────────────────┐
                    │        STM32F407VGT6          │
   MaixCAM (YOLO)    │                               │
   发送端 ──────────▶│ PB7  (USART1 接收)            │
   接收端 ◀──────────│ PB6  (USART1 发送, 不用)      │
                     │                               │
   模组接收端 ◀──────│ PB10 (原文写 USART3 发送；本板实为 PD8) │
   模组发送端 ──────▶│ PB11 (USART3 接收)                     │
                     │                                        │
   现行方案：脉冲 + 方向，两台 Emm42 各占一路（不再是"共用总线"）
   水平 Emm42 ◀──────│ PB10 (TIM2_CH3 脉冲) / PA4 (方向)      │
   俯仰 Emm42 ◀──────│ PA3  (TIM5_CH4 脉冲) / PA5 (方向)      │
                     │                               │
   激光驱动输入 ◀────│ PC13 (激光)                   │
                     └───────────────────────────────┘
      所有设备必须共地（地线相连）；电机驱动电源与单片机电源分开供电，避免电机电流干扰串口
```

> 💡 **没有 MaixCAM 也能验这条链路**：把 USB 转 TTL 的 `TXD` 接到 **`PB7`**
> （`RXD` 仍接 `PB10` 看心跳），用串口助手冒充 MaixCAM 发 `cx,cy,flag\n`，
> 心跳行里的 `rx=` 就会涨。这正是 **M3.3「串口助手冒充 MaixCAM」** 的做法，
> 验的是将来真正要用的那条路。见 `plan.md` §6.3 的上下游约定。


### 3.3 电机总线接线要点

1. **多机共用一条总线**：水平轴与俯仰轴挂在同一条 `USART2` 上，因此两台驱动器**必须设置成互不相同的串口地址**（本工程约定水平轴为 1、俯仰轴为 2，见 `AVE_PAN_MOTOR_ADDR` 与 `AVE_TILT_MOTOR_ADDR`）。
2. **驱动器菜单参数必须与固件一致**：波特率 115200、地址 1 与 2、校验字节 0x6B、串口模式为 `CR_UART`（不是控制器局域网，也不是脉冲/方向模式）。
3. **若使用 485 差分收发器**（A/B 差分接线）：需外接收发芯片，并注意自动换向模块的收发切换延迟 —— 固件为此保留了帧间隔 `AVE_MOTOR_TX_GAP_MS = 10 毫秒`、使能延迟 `AVE_MOTOR_ENABLE_DELAY_MS = 50 毫秒`、停止延迟 `AVE_MOTOR_STOP_DELAY_MS = 20 毫秒`。
4. **回读需串行化**：同一条接收线上多台电机不能同时应答，固件在 `AVE_ZdtMotor_Request()` 中限制"同一时刻仅允许存在一个未完成的读请求"。

### 4.2 FreeRTOS 任务划分与调度

> **本节相对原方案的变化**：原方案是裸机超级循环（`main()` → 初始化 → `while(1)` 调 `AVE_App_Loop` + `HAL_Delay(1)`），
> 所有职责挤在同一个上下文里。这带来两个无法回避的问题：
>
> 1. **任何一处阻塞都会拖住全部功能** —— 一次 ESP8266 的 AT 指令等待（超时以秒计）、一次长报文串口发送，期间 PID 控制环完全停摆；
> 2. **时序无法保证** —— 控制周期被最长的那次阻塞拉长，50 赫兹的硬实时约束形同虚设。
>
> 改为 FreeRTOS 后按职责拆分任务，阻塞只影响自身。

#### 4.2.1 任务表

| 任务 | 优先级 | 周期 / 触发 | 职责 | 栈（字节） |
| --- | --- | --- | --- | --- |
| `VisionTask` | `osPriorityHigh` | 20 毫秒（50 赫兹），`osDelayUntil` | 排空视觉串口完整行 → 取最新一帧 → 死区判断 → PID → 符号映射 → 下发转速 → 断流超时检查 | 1024 |
| `MotorTask` | `osPriorityAboveNormal` | 10 毫秒 | 解析电机总线应答（通用应答 / 定位完成 / 回读数据）；开启回读时调度读请求 | 768 |
| `CmdTask` | `osPriorityNormal` | 10 毫秒 | 文本命令解析（本地与云端复用同一套） | 1024 |
| `CloudTask` | `osPriorityBelowNormal` | 10 毫秒 | 无线模组状态机 → MQTT 连接 / 订阅 / 心跳 / 上报 | 1536 |
| `StatusTask` | `osPriorityLow` | 2000 毫秒 | 云端状态上报（**仅 `AVE_ENABLE_CLOUD=1` 时创建**） | 512 |

**优先级分配理由**

- `VisionTask` 最高：它承担 50 赫兹控制环，是本系统**唯一的硬实时约束**；
- `MotorTask` 次之：电机应答已进环形缓冲区，容忍毫秒级解析延迟，但回读调度需要及时；
- `CmdTask` 再次：人在串口这头，几十毫秒无感；
- `CloudTask` 最低：网络往返以秒计，慢一点无影响，但**绝不能让它的阻塞影响云台**。

> 用 `osDelayUntil` 而不是 `osDelay`：前者按绝对时刻唤醒，周期不会随代码耗时漂移；
> 后者是"执行完再等 N 毫秒"，实际周期 = N + 执行时间，长期会偏。

#### 4.2.2 共享资源与互斥

电机总线被三个上下文同时使用，这是原方案（单上下文轮询）里不存在的新问题：

| 使用方 | 发起的操作 |
| --- | --- |
| `VisionTask` | 速度指令（`0xF6`） |
| `CmdTask` | 位置 / 使能 / 停止 / 零点 / 读回（`0xFD`、`0xF3`、`0xFE`、`0x0A`、`0x30`…） |
| `MotorTask` | 周期性回读请求 |

若不加保护，两个任务交错发送会让帧字节互相穿插，驱动器收到的就是垃圾。

**方案**：一把静态创建的 `osMutexId_t` 保护 `AVE_ZdtMotor_*` 的**全部发送接口**。

| 约束 | 说明 |
| --- | --- |
| 持锁时间 | 不得超过一个帧间隔（`AVE_MOTOR_TX_GAP_MS` = 10 毫秒）加最长帧发送时间（12 字节 ≈ 1.1 毫秒） |
| 禁止 | 持锁期间不得调用任何长阻塞接口（`osDelay`、信号量等待、AT 指令） |
| 优先级反转 | 启用 `osMutexPrioInherit` 属性，避免 `CloudTask` 意外拖慢 `VisionTask` |
| 例外 | **上电点动自检阶段调度器尚未启动**，不走互斥量，直接裸机发送 |

> 回读另有一条独立约束（见 3.3 节第 4 条）：同一时刻仅允许存在一个未完成的读请求。
> 该约束由 `MotorTask` 单独维护，与互斥量是两回事 ——
> **互斥量保证"不交错"，串行化保证"不撞车"。**

#### 4.2.3 初始化顺序（**两个入口**，按能不能碰 RTOS 切开）

> 🔧 **本节的标题与结构在 M1.5 实施时修正过。**
>
> 原方案写的是"一个 `AVE_App_Init()` 从板级初始化一路做到创建任务"。**做不到**：
> `main.c` 的 `USER CODE 2`（能调用初始化代码的唯一位置）在 `osKernelInitialize()`
> **之前**，而 `osThreadNew()` / `osMutexNew()` 必须在它**之后**才能调 ——
> 否则创建出的对象不会被内核接管，症状是任务一个都不跑，且没有任何报错。
>
> 于是按"**这一步要不要碰 RTOS 对象**"切成两个入口：

| 入口 | 调用于 | 职责 |
| --- | --- | --- |
| `void AVE_App_Init(void)` | `main.c` USER CODE 2（`osKernelInitialize()` 之前） | 纯外设：板级初始化、绑句柄、启动接收、上电自检、安全动作。**不碰任何 RTOS 对象** |
| `int AVE_App_RtosInit(void)` | `freertos.c` USER CODE `RTOS_THREADS`（内核已初始化之后） | 创建互斥量与全部任务。返回 `0` 成功 / `-1` 失败 |

**`AVE_App_Init()` —— 纯外设部分**

1. 板级初始化：激光通用输入输出 → 视觉串口 → （云端开启时）无线模组串口 → 电机串口 → （脉冲后端开启时）定时器 6；
2. 绑定串口句柄并启动逐字节中断接收（视觉、电机、以及可选的模组串口）；
3. 云台聚合初始化 + **上电即使能电机**（向两轴驱动器使能）；
4. **上电点动自检**（`AVE_ENABLE_STARTUP_MOTOR_TEST=1`）：水平轴以 300 转/分转 300 毫秒 → 停止 → 间隔 150 毫秒 → 俯仰轴同样动作 → 间隔 150 毫秒。用于快速验证接线、地址与转向。
   > 此时调度器尚未启动，延时直接用 `HAL_Delay`（`TIM7` 时基已在 `HAL_Init()` 中生效）。
5. 视觉跟踪初始化：清零 PID 并执行一次「目标丢失」安全动作（关激光 + 停两轴）；
6. （可选）无线模组初始化 → 云端初始化。

**`AVE_App_RtosInit()` —— 创建内核对象**

7. 创建电机总线互斥量（属性带 `osMutexPrioInherit`）；
8. 创建全部任务（视觉 / 电机 / 命令 / 心跳），**逐个检查返回值**；
9. 调用方（`freertos.c`）拿到 `0` 才继续 `osKernelStart()`；拿到 `-1` 进 `Error_Handler()`。

> 🔴 **`osThreadNew` 失败时返回 `NULL`，不会报错、不会死机，任务直接不存在。**
>
> 最常见的原因是 `configTOTAL_HEAP_SIZE` 不足。**必须逐个检查返回值**，任一为 `NULL`
> 立即进入 `Error_Handler()` —— 否则你会得到
> 「上电一切正常，但某个功能永远不工作」这种极难定位的现象。

**🔴 分工为什么不能"简单点"合并回去**

把 `AVE_App_RtosInit()` 并进 `main.c` 的 `USER CODE 2`、在 `osKernelInitialize()` 之前调用，
**编译链接全过、上电不报错、任务一个都不跑**。这是本工程目前为止
最容易"看起来正常"的一类错误 —— 它没有任何运行时症状，只有"什么都没发生"。

**🔴 关键改动：`vApplicationStackOverflowHook` 必须置标志，不能在里面打印**

如果钩子里调 `AVE_Log()`，而栈溢出本身已经吃掉了可用栈，
`vsnprintf` 会在**已经溢出的栈**上再开缓冲 —— 行为不可预期。
正确做法是只写两个全局变量（`AVE_AppStackOverflow` / `AVE_AppStackOverflowTask`），
由心跳任务发现标志后再打印。这样连"哪个任务溢出"都能报出来。

#### 4.2.4 报错传播

| 情况 | 处理 |
| --- | --- |
| `osThreadNew` / `osMutexNew` 返回 `NULL` | `AVE_App_RtosInit()` 返回 `-1` 并把名字存进 `AVE_App_FailName`，调用方 `Error_Handler()` |
| `osKernelInitialize` 失败 | 同上 |
| 任务内部可恢复错误（串口溢出、电机无应答） | 累加统计计数，不影响任务存活 |

> 🔧 **"打印失败对象名"这一条在实施时改掉了。**
>
> 失败发生在**调度器启动之前**。此时串口即便能写，也只是把字节塞进驱动，
> 没有任何东西会把它送上线路 —— `AVE_Log()` 在这个位置是**静默无效**的，
> 而且会让写代码的人以为自己已经报过错了。
>
> 改为：名字存进 `const char *volatile AVE_App_FailName`（调试器 Watches 里直接看），
> 由 `freertos.c` 的调用方进 `Error_Handler()`。**不要在调度器启动前指望任何输出。**

#### 4.2.5 中断

| 中断 | 抢占优先级 | 处理 |
| --- | --- | --- |
| `USART1_IRQHandler` / `USART2_IRQHandler` / `USART3_IRQHandler` | 5 | `HAL_UART_IRQHandler()` → 接收完成回调（`AVE_isr.c`）→ 该字节写入对应环形缓冲区 → 重新武装接收 |
| `TIM7_IRQHandler` | 15 | `HAL_IncTick()`（HAL 时基） |
| `TIM6_DAC_IRQHandler` | 5 | 脉冲节拍分发（仅脉冲后端启用时有效，默认不启用） |

> 🔴 **中断服务程序的纪律**（违反其中任何一条都会造成偶发、难复现的故障）：
>
> 1. 不得调用 `HAL_Delay`，不得任何形式的忙等；
> 2. 不得调用会阻塞的 RTOS 接口 —— `osDelay`、`osMutexAcquire`、`osSemaphoreAcquire` 一律禁止；
> 3. 需要唤醒任务时用 `osSemaphoreRelease` / `osMessageQueuePut` / `osEventFlagsSet`（这些在 CMSIS-RTOS2 中允许在中断里调用）；
> 4. 中断里只做「取字节、写缓冲、更新计数、退出」，不做解析、不做浮点、不做字符串处理。
>
> 优先级 **5** 是 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` 的边界值 ——
> **等于 5 可以调用上述中断安全接口，小于 5 则绝对禁止**（见 2.1 节）。

### 4.3 视觉跟踪控制律

- 输入：像素坐标与标志位；水平偏差 = 目标横坐标 − 画面宽度一半，俯仰偏差 = 画面高度一半 − 目标纵坐标（纵轴方向已取反）；
- **增量式 PID**：输出增量 = 比例项增益 ×（本次误差 − 上次误差） + 积分项增益 × 本次误差 + 微分项增益 ×（本次误差 − 2 × 上次误差 + 上上次误差），输出值在正负最大转速之间累加限幅；
- 死区：偏差绝对值不超过 `AVE_VISION_TOL_PX`（8 像素）时，该轴**停止累加并保持上一次输出**（不硬清零），同时把前两次误差跟进为当前值；两轴死区独立判断；

  > ⚠️ **原方案写的是「输出 0 并复位 PID」，已修正。** 这么写有两个问题：
  >
  > 1. **直接清零输出会让云台在死区边缘一顿一顿** —— 电机反复启动 / 停止，机械上表现为明显抖动与噪声；
  > 2. **复位误差历史会在目标重新移出死区的瞬间产生虚假的微分尖峰** ——
  >    微分项 = Kd × (e − 2·e_prev + e_prev2)，历史被清零后 `e_prev = e_prev2 = 0`，首拍微分项退化成 Kd × e，是个冲击。
  >
  > 正确做法是**冻结**而非**清零**：输出保持不变，误差历史跟进为当前值。
- 符号映射：`AVE_VISION_PAN_SIGN = +1`、`AVE_VISION_TILT_SIGN = -1`（由机械安装方向决定）；
- 输出：以**转/分**为单位，经 `0xF6` 速度模式下发；仅当目标值发生变化时才发送，两轴都需发送时插入 10 毫秒帧间隔；
- **延迟是调参的第一约束**：本闭环里最大的滞后来自视觉链路（曝光 + 推理 + 串口），合计约 **50～100 毫秒**，
  远大于控制周期本身。**它直接限制比例增益 `Kp` 的上限** —— 总延迟翻倍，可用 `Kp` 就要减半。
  因此在"减小 `Kp`"之前，应先考虑"缩短延迟"（降低 MaixCAM 采集分辨率 / 换更小的模型）。延迟预算见 §6.4；
- **安全策略**：
  - 目标坐标出现负值（无目标）时 → 复位 PID、关闭激光、**立即停止两轴**；
  - 视觉数据流超过 `AVE_VISION_RX_TIMEOUT_MS = 200 毫秒` 无更新 → 判定断流，同样停机并关激光。

### 5.2 串口抽象模块（`AVE_uart.c` / `AVE_uart.h`）

| 项目 | 内容 |
| --- | --- |
| 职责 | 统一收发接口 + 1024 字节环形缓冲区 + 按行读取 |
| 机制 | 每次中断只接收 1 字节，回调中写入环形缓冲区后重新武装接收；写指针由中断维护、读指针由主循环维护；缓冲区写满时丢弃新字节 |
| 关键接口 | 句柄绑定、启动中断接收、按行读取、按字节读取、按字节发送、按字符串发送、**非阻塞发送（`AVE_Uart_WriteIT`）**、**查询发送忙（`AVE_Uart_TxBusy`）**、清空接收缓冲、中断接收完成处理 |
| 注意事项 | 按行读取只认换行符 `\n`，会自动剥离回车符 `\r`，没有换行符时不返回。115200 波特率下每个字节触发一次中断；**主频必须为 168 兆赫**，开销核算见 2.1 节 |
| 🔴 RTOS 发送约束 | 原方案的「阻塞式发送」在 RTOS 下**必须分类处理**，不能一刀切：<br>• **定长控制帧（≤ 16 字节）** —— 如 ZDT 电机指令，保留阻塞式。115200 下一帧最长（12 字节）仅约 1.1 毫秒，代价可接受，但**必须持有电机总线互斥量**（见 4.2.2）；<br>• **长度不定的输出** —— 调试日志、JSON 状态上报、MQTT 报文，改用**中断或 DMA 发送 + 发送完成回调**，禁止在任务里阻塞等待；<br>• **任何 `HAL_UART_Transmit` 的 `Timeout` 参数都必须显式给出，且 ≤ 100 毫秒**，严禁使用 `HAL_MAX_DELAY` |
| 🔴 中断发送的三条实现纪律 | 1. **先拷后发**：`HAL_UART_Transmit_IT` 只记录指针，调用方的内存必须活到发完才有效。`AVE_Uart_WriteIT` 先把数据拷进模块自己的 `s_tx_buf` 再启动发送，调用返回后调用方可以立刻覆盖原缓冲；<br>2. **必须有发送完成回调**：`HAL_UART_TxCpltCallback` 里清忙标志。少了它，忙标志永远不清 → **日志打几条后永久沉默**，而所有状态字看起来都正常；<br>3. **错误回调要清两个方向**：`HAL_UART_ErrorCallback` 是收发**共用**的。只 `AbortReceive` 不清发送方向，一次接收错误就能让日志永久哑掉。正确做法是 `AbortReceive` + `AbortTransmit` + 清忙标志 + 重新武装接收 |
| 发送失败时的行为 | **丢，不排队、不阻塞。** 上一笔没发完时 `AVE_Uart_WriteIT` 返回 `AVE_UART_EBUSY` 并累加 `tx_drop` 计数。理由：这是调试输出，为它阻塞控制环是本末倒置。**丢弃必须被看见**（计数进心跳行），否则"日志变少了"会被误读成"那段代码没跑到" |

**应答格式**

| 类型 | 结构 | 处理 |
| --- | --- | --- |
| 通用应答 | 地址, 应答码, 校验；应答码 `0x02` 为成功、`0xEE` 为错误、`0x9F` 为定位完成 | 成功置应答状态为 1；错误置为 2 并清除忙碌标志；定位完成清除忙碌标志 |
| 编码器 | 地址, 16 位无符号数, 校验（共 4 字节） | 更新编码器原始值 |
| 输入脉冲 / 实时位置 | 地址, 32 位有符号数, 校验（共 6 字节，**高位在前**） | 更新对应字段 |
| 位置误差 | 地址, 16 位有符号数, 校验 | 更新位置误差 |
| 使能 / 堵转 / 回零标志 | 地址, 8 位无符号数, 校验 | 更新对应标志位 |

要点：
- 解析器是**逐字节重同步**的状态机：遇到未知地址就丢弃 1 字节继续扫描，保证受干扰后能自行恢复；
- 结构体中的 `position_pulses` 是**软件累计**的命令位置（相对移动时累加），并非驱动器真实位置；真实位置需读取 `realtime_pos`；
- 角度换算：按驱动器手册，实际角度 = 实时位置 × 360 / 65536（代码注释给出该关系）；
- 回读请求受"同一时刻仅一个未完成读请求"限制，以避免多台电机同时应答造成冲突。

> 🔴 **量纲陷阱 —— 必须区分两套「一圈」**（这是最容易把角度算错 20 倍的地方）
>
> | 量纲 | 基准 | 出现在哪 |
> | --- | --- | --- |
> | **细分脉冲** | 3200 脉冲 = 1 圈（16 细分 × 200 步；以驱动器**实际**细分设置为准） | `0xFD` 位置模式**发送**的脉冲数、结构体里的 `position_pulses` 软件累计值 |
> | **编码器计数** | 65536 计数 = 1 圈（16 位） | `realtime_pos`、`input_pulses` 等**回读**字段 |
>
> 两者相差 **20.48 倍**。本节上面这句「实际角度 = 实时位置 × 360 / 65536」说的是**回读**量纲，
> 而 5.4 节的「脉冲数 = 角度 × 每度脉冲数」说的是**下发**量纲 ——
> 原方案把两句话并列写出却没有区分，照着标定会让角度整体偏 20 倍。
>
> 因此 `AVE_PAN_STEPS_PER_DEG` 的起步值应是 **3200 / 360 ≈ 8.889**（原方案的占位值 1.0 太随意），
> 且必须按驱动器**实际细分设置**重算后再实测修正。

| 项目 | 内容 |
| --- | --- |
| 职责 | 两台**步进电机**（各占一个定时器）的聚合薄壳：只做**角度 ↔ 脉冲的换算**与两轴**状态记账**。**不做** PID / 视觉下发 / 文本命令层 |

### 5.5 增量式 PID 模块（`AVE_pid.c` / `AVE_pid.h`）

| 项目 | 内容 |
| --- | --- |
| 结构 | 控制器结构体：比例增益、积分增益、微分增益、输出下限、输出上限、当前输出、前两次误差、初始化标志 |

| 开关 | `AVE_ESP_AUTOPROBE` 控制上电时是否发送基础 AT 指令探测（默认关闭） |
| 🔴 RTOS 约束 | 原方案的「阻塞式带超时」AT 指令（连接热点、建立传输控制连接等，超时以秒计）**必须改为非阻塞状态机**：<br>发出 AT 后立即返回，由 `CloudTask` 每 10 毫秒轮询一次响应，超时计数器随任务周期累加。<br>若不改，一次连接重试（3 秒）会让 `CloudTask` 独占处理器 3 秒。该任务优先级最低、影响相对可控，但仍会连带拖住心跳与状态上报。<br>**最低要求**：所有发送超时必须显式给出且 ≤ 100 毫秒，严禁无限等待 |

### 5.10 云端接入模块（`AVE_cloud.c` / `AVE_cloud.h`）

**状态机**

```
关闭 → AT 探测 → 设置为站点模式 → 连接无线热点 → 建立传输控制连接
     → MQTT 连接 → MQTT 订阅 → 就绪
```

| 状态 | 动作 | 失败重试间隔 |
| --- | --- | --- |
| AT 探测 | 发送 AT 测试、关闭回显 | 1 秒 |
| 设置为站点模式 | 设置为无线站点模式 | 1 秒 |
| 连接无线热点 | 使用凭据文件中的账号密码连接 | 3 秒 |
| 建立传输控制连接 | 单连接模式、关闭附加信息、关闭旧连接 → 连接消息服务器 | 3 秒 |
| MQTT 连接 | 发送连接报文（客户端标识优先取配置值，为空时由单片机唯一标识码生成，形如 `AVE-xxxxxxxxxxxxxxxxxxxxxxxx`） | 3 秒 |
| MQTT 订阅 | 订阅命令主题 | — |
| 就绪 | 抽取传输控制数据 → 解析 MQTT → 处理命令；**每 15 秒发送心跳**；**每 2 秒上报状态** | 检测到连接断开则回到"建立传输控制连接"状态（1 秒后） |

**下行命令**：订阅命令主题，数据内容直接交给单行处理接口解析，**支持多行数据**（按换行符拆行逐条执行），命令集与 5.7 节完全一致。

**上行状态**：每 2 秒以及连接建立成功时向状态主题发布一次数据内容（数据交换格式为 JSON）：

```json
{"pan_pulses":0,"tilt_pulses":0,"pan_rtpos":0,"tilt_rtpos":0,"busy":0}
```

| 字段 | 含义 |
| --- | --- |
| `pan_pulses` / `tilt_pulses` | 软件累计的命令脉冲数 |
| `pan_rtpos` / `tilt_rtpos` | 驱动器回读的实时位置（需实际发起过回读，否则为 0） |
| `busy` | 任一轴的忙碌标志为真则为 1 |

### 5.13 日志模块（`AVE_log.c` / `AVE_log.h`）

| 项目 | 内容 |
| --- | --- |
| 职责 | 一行非阻塞调试输出：格式化 → 定长缓冲 → 中断发送 |
| 接口 | `int AVE_Log(const char *fmt, ...)`；返回 `AVE_Uart_WriteIT` 的结果（`AVE_UART_EOK` / `AVE_UART_EBUSY` / `AVE_UART_EBADCH`） |
| 实现 | `vsnprintf` 写入调用者栈上的 `char line[AVE_LOG_LINE_MAX]`，补 `\r\n`，交给 `AVE_Uart_WriteIT(AVE_UART_DBG, ...)` |
| 调用上下文 | **只允许任务上下文**，禁止在中断里调用（`vsnprintf` 不可重入且耗时不可控） |
| 代价核算 | 60 字节 @115200 约 **5.2 毫秒**，而视觉周期是 20 毫秒 —— 所以绝不阻塞，发不出去就丢 |
| 🔴 栈的代价 | **每次调用都会在调用者栈上占 `AVE_LOG_LINE_MAX` 字节**，再加 `vsnprintf` 自己的内部开销。给日志任务分栈时必须把这一块算进去，否则会踩栈溢出。约束：`AVE_TASK_HEARTBEAT_STACK > AVE_LOG_LINE_MAX`（编译期断言） |
| 🔴 禁用 `%f` | 格式化浮点会一次性拉进整套浮点格式化代码，占数 KB 代码空间 + 不可控的栈用量。**所有数值一律先转成整数，用 `%lu` 打印** —— 温度、增益、误差都在打印前定标 |

> **为什么"丢弃"是可以接受的：** 调试日志的价值在于**看见趋势**，不在于**一条不漏**。
> 为一条日志去阻塞控制环，等于让日志反过来影响被观测的系统 —— 观测者效应。
> 但丢弃**必须可观测**：`tx_drop` 计数进心跳行，否则"日志变少"会被误读成"那段代码没跑到"。

## 6. 视觉端规格（MaixCAM + YOLO）—— 不在本固件内，但必须对齐

> **本章描述链路的上游。** 目标检测（YOLO 推理）在 **Sipeed MaixCAM** 上运行，
> 本固件（STM32F407）**只接收结果坐标**，不参与任何图像处理或神经网络运算。
>
> 之所以把它写进本项目文档：**上下游的坐标系、分辨率、发送节奏一旦不对齐，
> 症状全部表现为"云台乱转"，而在 STM32 侧完全看不出问题。** 这些约定必须写在纸上。

### 6.1 为什么 YOLO 不能跑在 STM32F407 上

| 需求 | STM32F407VGT6 | 结论 |
| --- | --- | --- |
| 神经网络加速单元（NPU） | 无 | ✗ |
| 算力 | 168 兆赫 Cortex-M4F，无单指令多数据流（SIMD）卷积加速 | 单帧数百毫秒至数秒 |
| 内存 | 192 千字节静态随机存储器，无外部内存扩展 | 一个 YOLOv5-nano 权重就约 2 兆字节 |
| **结论** | —— | **不可能。检测必须在 MaixCAM 侧完成** |

### 6.2 MaixCAM 侧的任务分解

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| 数据集 | 拍摄目标图像，覆盖不同距离、角度、光照；**另需 20～30 张"无目标"负样本** | 图片集 |
| 标注 | 单类别（本项目为单目标），矩形框紧贴目标边缘 | 标注文件 |
| 训练 | 上传 MaixHub 在线训练，选小模型 + 合适的输入分辨率 | `.cvimodel` 部署包 |
| 部署 | 先用官方例程包把模型跑通、屏幕上能看到框 | 可运行的 MaixPy 工程 |
| 输出 | 取**置信度最高的框** → 算中心 → 换算到采集图像坐标系 → 串口发送 | `cx,cy,flag\n` |

### 6.3 上下游接口约定（**硬约束**）

| # | 约定 | 违反的后果 |
| --- | --- | --- |
| 1 | **坐标系**：`cx`/`cy` 是**采集图像**（不是模型输入尺寸、更不是屏幕）的像素坐标，原点在左上角，Y 向下 | 画面中心算错，云台稳定偏在一侧 |
| 2 | **分辨率**：`AVE_VISION_SCREEN_W` / `_H` 必须**严格等于** MaixCAM 采集图像的分辨率 | 同上，且偏差随偏离中心线性增大 |
| 3 | **每帧必发**：无论有没有检测到目标，**每一帧都要发一行**；无目标时发 `-1,-1,0` | 只在有目标时才发 → 固件的 200 毫秒断流超时误判 → 云台反复停机 |
| 4 | **行尾**：以 `\n` 结尾（`\r\n` 亦可，解析器会剥离 `\r`） | 少一个 `\n` → 固件永远读不到完整行 → **完全无响应** |
| 5 | **波特率**：115200，8 位数据 / 1 位停止 / 无校验，与 `AVE_CAM_UART_BAUDRATE` 一致 | 全是乱码 |
| 6 | **发送频率**：建议 20～30 赫兹，**不要超过 50 赫兹** | 超过控制环频率无收益，只增加串口负载 |
| 7 | **共地**：MaixCAM 与 STM32 必须共地 | 电平无参考，通信随机失败 |
| 8 | **`flag` 值域**：只能是 `0` 或 `1`（`1` = 本帧有目标，`0` = 无目标） | 其它值（含 `-1`）→ 固件判**语法错整行丢弃** → 一帧都不被接受，表现为"什么都没发生" |
| 9 | **数字格式**：十进制整数，可有前导 `+`/`-`，**不超过 9 位**；字段间可有空白 | 超过 9 位 → 判语法错整行丢弃（位数上限是为了不给整数溢出留 UB 的入口，见 §5.6） |
| 10 | **行长**：一行不超过 **32 字节**（含 `\n`） | 整行丢弃并计 `line_spilled`。⚠️ 这一条最容易在"顺手在视觉口多打点调试文本"时违反，而现象同样是"什么都没发生" |

> **第 8～10 条是 2026-09-26 第十四次从代码回写进规格的**：原文只给了例子
> （`320,240,1` / `-1,-1,0`），没有给值域、位数与行长。这三条是**契约**，
> 不能由实现私自决定 —— 对方按原文字面发 `320,240,-1` 或 10 位坐标，
> 固件会静默丢弃，而**静默丢弃在两端看起来都像成功**。

> **接线只需走单向**：本固件不使用 `USART1` 发送，因此只需
> `MaixCAM 发送端 → STM32 PA10` 与 `地 → 地` 两根线（`PA9` 可悬空）。
> 双方电平都是 3.3 伏特，直连即可，无需电平转换。

### 6.4 延迟预算（决定 PID 能调多快）

| 环节 | 典型耗时 |
| --- | --- |
| 相机曝光 | 10～30 毫秒（暗环境更长） |
| YOLO 推理 | 20～50 毫秒（取决于模型大小与输入分辨率） |
| 串口传输（约 10 字节 @115200） | 约 1 毫秒 |
| 固件控制周期（50 赫兹） | ≤ 20 毫秒 |
| **合计** | **约 50～100 毫秒** |

> 🔴 **这 50～100 毫秒是闭环里最大的滞后环节，它直接限制比例增益 `Kp` 的上限。**
>
> 经验关系：**总延迟翻倍，可用的 `Kp` 就要减半。** 所以当云台怎么调都振荡时，
> **优先缩短延迟**（降低 MaixCAM 采集分辨率 / 换更小的模型 / 提高推理速度），
> 而不是一味减小 `Kp` —— 后者会让响应变慢并留下稳态误差。
>
> 另外：YOLO 输出的框中心**每帧有 ±2～3 像素抖动**，会被微分项放大成电机的高频嗡鸣。
> 因此视觉伺服里 **`Kd` 通常取很小的值甚至为 0**；必要时在固件侧对 `cx`/`cy` 加一阶低通滤波
> （`AVE_VISION_FILTER_ALPHA`，默认关闭）。

| `AVE_ESP_AUTOPROBE` | 0 | 上电是否发 AT 探测 ESP8266（仅云端开启时有意义） |

| `configTOTAL_HEAP_SIZE` | 32768 | FreeRTOS 堆大小（`Core/Inc/FreeRTOSConfig.h`）。**必须核对** —— 堆耗尽时 `osThreadNew` 只返回 `NULL`，不报错、不死机 |

### 7.3 建议的上电调试顺序

1. **只接电机总线**，把视觉开关与云端开关置 0，上电观察自检点动：两轴应各自转动约 0.3 秒。
   - 只有一轴动 → 检查地址是否唯一、驱动器菜单中的地址与波特率与校验字节、接线方向（收发是否交叉）；
   - 两轴都不动 → 检查总线电平类型（单端电平还是 485 差分）、是否共地、驱动器供电与使能。
2. 用串口助手在视觉串口上发文本命令验证运动：
   `EN 1` → `SPEED 800` → `PAN 10` → `TILT -5` → `STOP` → `ZERO` → `QPOS`。
3. **标定每度脉冲数**：发 `PAN 360`，实测转过的角度，按"新系数 = 现有系数 × 360 ÷ 实测角度"修正。
4. 打开回读开关，观察实时位置是否随动（注意 5.3 节所述回读串行化限制）。
5. 接入 MaixCAM 并打开视觉开关，先用较小的比例增益（如 0.05）起飞，再逐步加大到不振荡；死区太小会抖动，太大会有静差。**调不起来时先怀疑延迟，不要只减 `Kp`**（见 §6.4）。
6. 最后再打开云端开关，先用 MQTT 客户端订阅状态主题观察上报，再向命令主题发命令。

# 项目规则（必须遵守）

> 本文件由 Claude Code 在每次会话开始时自动加载。

---

## 规则 0 · 读取范围约束（用户 2026-09-26 定下的固定规则）

**这六条约束的是"我能看什么"，优先于任何分析便利。**

1. **禁止一次性扫描整个工程**，禁止自动遍历全部源码，禁止全盘读取所有文件。
2. 分析当前模块时，**可以**读取该模块配套的业务 `.c`/`.h` 代码。
3. **STM32 HAL 库、芯片底层系统头文件，一律不需要读取。**
4. **同一个文件，本次会话最多读取 1 次**，禁止重复读取同一个文件。
   - 要新位置就**精确 grep**，或只读需要的行段；不要为了"确认一下"再通读一遍。
   - 例外：文件在本轮被改过、需要核对改后行号时可以再读那一段。
5. **分模块开发**：当前模块分析、编写完成之后，再进入下一个模块。
6. **没有用户确认，不主动浏览文件夹目录**（不跑 `ls`/`dir`/`find`/全目录 glob 去"看看有什么"）。
   杜绝的是【**扫描目录 → 自动批量读取文件**】这条链：一旦列了目录，就很容易顺手把
   列出来的东西都读一遍，那正是规则 ① 要禁的。**要读哪个文件，先问用户。**

**为什么**：这个工程有 CubeMX 生成物、HAL 驱动、Middlewares 等大量与业务无关的代码，
全量扫描既烧上下文又会被无关信息带偏。**要读哪个文件，先问用户**——这比自己猜一遍再返工便宜。

### ✅ 明确允许的一项（用户 2026-09-26 补充说明）

```
wc -l plan.md verify.md ROADMAP.md temporary.md
```

- **允许执行**，理由是规则 4 要求每轮量这四份文档的行数；
- 它统计的是**固定命名的 4 个 `.md` 文档**，**不属于浏览目录，也不属于遍历文件**；
- 它**只数行数，不做业务源码解析**，因此**不受规则 ④「同一文件会话只读一次」约束**
  —— 那一条管的是**读源码内容**，不是数行数。

**违反的典型症状**（自查用）：忽然开始 `ls` 整个目录、对同一文件读第二遍、
为了找一个符号把 `Drivers/` 也搜了、一次改动横跨两个不相干的模块。

## 规则 1 · 上下文溢出交接（最高优先级）

**触发条件：对话上下文窗口占用超过 70%。**

一旦触发，立即执行以下四步，**不得继续当前开发**：

1. **立即停止当前任务**，向用户声明「上下文溢出」。
2. 整理当前工作进度，明确列出三项：
   - 已完成项
   - 未完成项
   - 下一步计划
3. 将工作计划写入项目根目录 `temporary.md`（不存在则创建）。
4. 提示用户新开对话窗口，并输入：

   ```
   请提取temporary.md
   ```

**优先级声明：上下文溢出交接的执行优先级，高于当前正在执行的任何开发任务。**
即使代码只写了一半、正处于关键改动中间，也必须先停下来完成交接。

## 规则 2 · 完成任务后必须自测

完成用户要求的任务（任务计划见 `plan.md`）后，必须自行创建一个测试并**实际运行或审查**，确认改动能达到预期效果。

**硬性约束：只保留一份 `verify.md`。**
每次验证复用同一个文件，覆盖更新即可，禁止创建 `verify1.md`、`verify2.md`、`verify_final.md` 之类的多份验证文档。

自测结果如实汇报：通过就说通过，失败就把实际报错或实测输出贴出来，不要含糊带过。

## 规则 3 · 每次改动后必须交一份"看得懂"的说明（教学交付）

**触发条件：任何对 `.c` / `.h` 文件的改动**（含 CubeMX 的 `/* USER CODE BEGIN */` 块、测试脚手架、构建脚本）。
纯文档改动（`verify.md` / `plan.md` / `ROADMAP.md` 等）只需一句话说明改了什么。

改完代码后，**在同一条回复里**按下面五节交付。**顺序不许调换，3.1 / 3.3 / 3.4 一节都不许省。**

### 3.1 改动位置清单（表格，必交）

| 文件:行 | 改前 | 改后 | 为什么 |

- 必须写成 `AVE/AVE_vision.c:284` 这种**可点击的相对路径**，不许只说"改了视觉模块"。
- 新增文件写"新增（N 行）"；被删掉的行必须原样写出来。
- 行号要真实。**不许估** —— 拿不准就去读文件。

### 3.2 代码解读（必交）

逐段讲：**这段在干什么 → 为什么这么写 → 不这么写会怎样**。
面向的是"看得懂 C 语法、但没写过 RTOS 工程"的人，所以：函数逐个过、关键变量逐个解释、用到的宏要展开讲。

### 3.3 系统视角（必交）

固定回答这七问，**用表格**：

| 问题 | 本次答案 |
| --- | --- |
| 任务/中断启动顺序 | 谁先谁后，各自在哪个文件哪一行 |
| 业务逻辑主线 | 数据从哪来、经过谁、到哪去（一条链） |
| 实现方式 | 中断 / 轮询 / DMA / 定时器 / 回调 / 阻塞延时 —— 分段写清各是哪一种 |
| 用到的结构体 | 名字 + 每个字段干什么 |
| 用到的宏 | 名字 + 当前值 + **谁在检查它** |
| RTOS 机制 | 任务优先级 / 周期 / 栈、`osDelayUntil`、互斥量、队列、信号量、事件标志 |
| 任务之间怎么通信 | 共享变量？消息队列？各自独占？有没有竞争，靠什么挡住 |

### 3.4 图表（必交）

- 至少**一张表**。
- 只要涉及流程，就给 **ASCII 流程图** —— 终端和 VSCode 都能直接看，不依赖 mermaid 渲染。
- 涉及"两个任务抢同一个东西"或"严格时序"，给**时序图**。
- 只贴代码不给图，等于没讲 —— "看不懂"通常缺的正是图。

### 3.5 代码里的注释（写代码时就要写，不等用户来要）

- **文件头块**：这个文件负责什么、**不**负责什么、有哪几条"不许破坏"的硬约束。
- **函数头块**：功能 / 参数 / 返回 / **谁调用它** / **什么时机调用** / 有什么坑。
- **行内注释**：只注释**非显然**的行，写**为什么**，不只是"做了什么"。
  反例：`i++; /* i 加一 */`。正例：见 `AVE_vision.c:218` 那段"范围校验为什么不能提前"。
- 注释语言：中文（本工程既有约定）。

### 风格基准（江协科技 + 韦东山）

1. **讲取舍**：每个不显然的决定，都要写出**被否决的那个方案**和否决它的实测理由。
2. **给现象**：写清"错了会看到什么"——「云台一追就逃」「串口上少了一行」「看起来像调参问题」。
   这是排查现场故障时**唯一**有用的线索，比"这里很重要"有用一百倍。
3. **不吹牛**：测了写✅、没测写⬜，禁止"已优化""应该没问题""基本完成"这类含糊词。
   **注释里不许写没验证过的结论** —— 本工程已经犯过一次（把 0/1 标志当计数，算错了 `[VS]` 行宽）。

### 优先级

**规则 1 > 规则 2 > 规则 3。**

规则 3 的篇幅要求**不能**用来推迟自测、更不能用来掩盖失败。
一次改动很大时，可以先交 3.1 + 3.3，其余下一轮补齐，但必须明写"补"、不许留着不提。

## 规则 4 · 文档有上限，每轮结束必须压缩收尾

**适用于四份文档：`plan.md` / `verify.md` / `ROADMAP.md` / `temporary.md`。**

### 4.1 硬上限：每份 **≤ 1000 行**

- 写完任何一轮之后，`wc -l` 量一遍这四份，**超了就当场精简，不许拖到下一轮**。
- 精简是**压缩**不是删除。以下内容**一条都不许丢**：
  1. **所有失败记录 / 误诊 / 撤回的结论**（「我下错了结论」「差点假绿」这类）——这是文档最贵的部分；
  2. **所有 ⬜ 未验证项 / ⚠️ 诚实边界**——"没测什么"比"测了什么"更容易被误读；
  3. **所有 🔴 隐患 / 待用户裁决项**；
  4. **所有实测数字**与**未完成里程碑的可执行细节**（下一步要照着做的，不能压没）。
- 可以删的：重复段落、抒情式铺陈、原始命令输出（每段留 3~10 行判别性输出即可）、
  同一概念的反复解释、**已经完成的里程碑**的逐条过程描述（结论 + 数字保留，细节在 `verify.md` 里）。
- 压完必须**自查一遍**：拿关键字 grep 一遍（轮次编号、`⬜`、`plan.md:` 的引用、关键数字），
  确认压缩没有把留痕压没。

### 4.2 每轮对话结束时的收尾动作（顺序固定）

1. `wc -l` 量四份文档；
2. 超限的当场精简到 1000 行以内；
3. 把本轮的结论按下面的分工写进对应文档：

| 文档 | 写什么 | 不写什么 |
| --- | --- | --- |
| `verify.md` | 本轮的**实测证据**（数字、命令输出、失败留痕、未验清单），按「第N次」小节 | 冗长过程；下轮计划 |
| `ROADMAP.md` | 里程碑状态的**变更** + 新发现的坑 + 附录 D 勾选 | 逐条过程；实测输出 |
| `temporary.md` | **交接给下一个对话窗口**的内容：当前进度一句话、下一步①②③、待用户裁决项 | 历史过程 |
| `plan.md` | 只有**设计规格**变了才动（用户的设计文件，改前先报） | 进度、验证结果 |

4. **压缩上下文**：本轮结束时把"下一轮要用到的信息"提炼进 `temporary.md`，
   使下一个对话窗口**不必重读全部历史**也能接手 —— 这正是规则 1 那套交接机制的日常版。

### 4.3 与规则 1 的关系

规则 1 是**被迫**的交接（上下文溢出，最高优先级）；规则 4 是**主动**的收尾。
两者共用同一份 `temporary.md`，格式一致 —— 所以规则 4 做得好，规则 1 触发时几乎不用额外工作。
